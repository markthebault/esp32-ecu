# Project-local NVS recovery correction

Runtime files are copied from the pinned PlatformIO `framework-espidf` package `3.50500.0`, under Espressif's Apache-2.0 license. The installed SDK is unchanged. ESP-IDF's project component precedence selects this directory for firmware builds. `ecu-source-manifest.json` records every original and project file hash; only one upstream source line differs. The accompanying patch adds the existing item's chunk index to the final active-page duplicate lookup in `Page::mLoadEntryTable`.

An independently authored memory-backed flash-error test reproduced a lost committed blob after an unsuccessful replacement. An old final chunk and the new first chunk occupied one still-active page. Restart duplicate cleanup matched by namespace/type/key while ignoring the distinct chunk index, erased the old chunk, and later discarded its incomplete old blob index. Supplying `item.chunkIndex` preserves the two distinct records. Nonblob items retain their existing `CHUNK_ANY` semantics. Page-manager duplicate cleanup already supplies this field.

The unchanged and corrected source variants are compared with the same fault sequence, normal repeated saves and nonblob controls. This is source-level fault injection, not physical brownout, torn-write, flash-wear or power-cut qualification. No flash partition is moved or enlarged; engine JSON remains bounded at 48 KiB in the existing 128 KiB engine partition. NVS remains shared infrastructure for its normal callers, so firmware builds and ordinary sensor/peer/configuration checks must accompany the storage regression.

Upstream references: [pinned source family](https://github.com/espressif/esp-idf/blob/v5.5/components/nvs_flash/src/nvs_page.cpp), [NVS storage design](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32s3/api-reference/storage/nvs_flash.html). Exact installed hashes, rather than the reference tag alone, identify the tested source. No upstream issue or patch has been submitted by this task.
